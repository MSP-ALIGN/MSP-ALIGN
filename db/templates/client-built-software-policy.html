Client-Built Software Policy

{{client_name}} · Effective {{today}} · Maintained with {{company_name}}

1. Purpose

Software that {{client_name}}'s own staff build runs on company devices only after {{company_name}} has reviewed, packaged and signed it. Staff increasingly build their own tools with AI coding assistants, and those tools often handle confidential data with no review behind them. This policy sets the gate between that code and company devices, so a tool built in an afternoon can't quietly send client data somewhere it shouldn't go.

2. Scope

This policy covers scripts, desktop applications, browser extensions, macros and automations written by {{client_name}} staff or contractors, whether AI-assisted or not. It does not cover commercial software, which follows the normal software approval process in the Asset Management Policy.

3. Roles and responsibilities

The developer owns the code. {{company_name}} owns the gate between that code and company devices, and does not write or fix the code.

  • Developer ([name, title]): writes the code, fixes bugs, builds updates and documents how the tool works. Does not deploy to devices, sign software or work around the review.
  • Sponsor ([name, title], e.g. office manager or owner): approves the tool for business use, accepts any remaining risk in writing, and approves billable review time. Not responsible for the technical review.
  • {{company_name}}: reviews the code and data flow, tests, packages, signs and deploys the tool, and keeps the version records. Does not write features, fix bugs or maintain the code.

Problems found during review are documented and sent back to the developer. Any development work by {{company_name}} is a separate, quoted project approved by the sponsor, never part of routine review.

4. Intake

Review starts only once the developer has handed over everything below. A partial submission goes back without review.

  • ☐ Full source code, any build or launch files, and a list of every dependency with its version
  • ☐ A plain-language description of what the tool does and who will use it
  • ☐ Where data goes: whether documents are processed on the device or sent to an AI service or other outside service, and which one
  • ☐ Any API keys, accounts or subscriptions the tool relies on, and whose name they are in
  • ☐ Sample input files and the expected output
  • ☐ Written approval from the sponsor to proceed

5. Review checklist

Data flow is checked first, because a bad answer there ends the review before any code is read. A tool passes only when every item below is cleared, or the sponsor has accepted the risk in writing.

  • Data flow: whether company or customer data leaves the device, where it goes, and whether that service's terms allow it to keep the data or train on it. Restricted and Confidential data follow the Data Classification & Handling Policy.
  • Outbound connections: every network call in the code matches what the developer described, confirmed by watching the traffic during testing.
  • Secrets: no API keys, passwords or tokens written into the source.
  • Dependencies: every package comes from a known source, is pinned to a version and has no known vulnerabilities.
  • Permissions: runs as a standard user, with no administrator rights, no security tools turned off and no start-up entries or services it doesn't need.
  • Function: does what it claims with the sample files and fails safely on bad input.
  • Output: for tools that change documents, the output itself is checked, not just the code (for redaction, text extraction or metadata removal, confirm the removed content is really gone).
  • Logging: doesn't write sensitive content to logs, temporary folders or cloud sync folders.

The findings and the reviewed version number are kept in {{client_name}}'s documentation.

6. Packaging, signing and deployment

The installer is built from the exact code that was reviewed, so what lands on devices is what was checked.

  1. {{company_name}} builds the installer from the reviewed source, never from a file the developer supplies.
  2. The installer is signed with [a code-signing certificate issued to {{client_name}} / {{company_name}}'s code-signing certificate], and its version, file hash and review date are recorded.
  3. It is deployed through {{company_name}}'s device management to the devices the sponsor approved.
  4. Where application control is in place, only the signed file's hash is allowed, so an unreviewed copy can't run.

7. Updates and change control

Every update goes through the same intake, review and packaging steps as the first release, with no exceptions for small changes.

  • The developer submits the full updated source with a short note on what changed and why.
  • Review can focus on the changes since the last approved version, but data flow and outbound connections are checked again every time, since a one-line change can start sending data somewhere new.
  • Each approved version gets a record of its version number, file hash, review date and reviewer, kept in {{client_name}}'s documentation.
  • Old versions are removed from devices when the new one is deployed.
  • Urgent fixes still go through review. They can be prioritized, but the review is never skipped.

8. Billing, support and retirement

[Optional: review, packaging and deployment time is billable project work, not covered by the managed services agreement, and the sponsor approves it before work starts.]

  • Support: {{company_name}} supports the installation and deployment. Questions about how the tool behaves, and any bugs, go to the developer.
  • Breakage: if an operating system or dependency update breaks the tool, {{company_name}} can roll back to the last approved version, but the fix comes from the developer.
  • Ownership: {{client_name}} owns the code and keeps a copy of the source outside the developer's personal accounts.
  • Developer leaves: if the developer leaves or stops maintaining the tool, it stays at its last approved version until a new developer is named. If none is named within [90] days, or a security problem is found, it is removed.
  • Retirement: when a tool is retired, {{company_name}} uninstalls it from all devices, and any API keys or accounts it used are revoked.
  • [Optional: Liability: the service agreement with {{company_name}} states that {{company_name}} is not liable for the behavior of client-built software it reviews.]

9. Enforcement

Running, installing or sharing client-built software that hasn't been through this review, or changing a reviewed tool without review, is not allowed. Unreviewed tools found on company devices are removed, and the sponsor is told.
